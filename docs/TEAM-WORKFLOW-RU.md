# Команда OxyMac Cleaner

Согласованные роли: 15 октября 2026 года. Это порядок совместной работы, а не подтверждение завершения проверок продукта.

## Роли

| Роль | Ответственность | Результат работы |
| --- | --- | --- |
| Пользователь и ведущий разработчик | Пользователь задаёт приоритеты; ведущий разработчик согласует решения, реализует и интегрирует изменения, отвечает за выпуск | Проверенные изменения и честный статус сборки |
| Продуктовый аналитик | Цели, сценарии, лишние шаги, состояния ошибок, критерии полезности | Приоритетные проблемы и проверяемые критерии приёмки |
| Дизайнер | Прототипы, состояния экранов, тексты, визуальная иерархия, доступность, темы | Макеты с описанием поведения, основанные на текущем продукте |
| Технический писатель | ТЗ, инструкции, история решений и соответствие документации реализации | Актуальные документы без смешения планов и выполненного |
| QA | Сценарии, регрессии, автотесты, проверка сборки и обновления | Воспроизводимые дефекты и отчёт с границами проверки |

## Рабочий цикл

1. Аналитик описывает проблему пользователя и критерии успеха.
2. Дизайнер прорабатывает нужные состояния и прототип; писатель обновляет требования по принятому решению.
3. Ведущий разработчик проверяет техническую реализуемость и вносит изменения.
4. QA проверяет критерии, негативные сценарии и существенные регрессии; полезные автотесты остаются в репозитории.
5. Писатель сверяет итоговые документы. Ведущий разработчик сообщает, что проверено, что установлено и что опубликовано.

Небольшое исправление не требует обязательного прохождения всех ролей. Не расширяем выпуск новыми пожеланиями до закрытия текущих дефектов.

## Правила совместной работы

- Все роли соблюдают инструкции Codex и применимые AGENTS.md/skills. Роль не даёт дополнительных разрешений.
- При четырёх одновременных слотах ведущий разработчик и максимум три специалиста работают параллельно; четвёртый специалист подключается после завершения одной задачи.
- Задания содержат границы, ожидаемый результат и разрешённые файлы. Первый аудит проводится без правок.
- Код и документация общие: перед изменениями проверяем актуальный diff; один файл одновременно меняет один исполнитель.
- GUI и установленной копией приложения управляет один исполнитель. Остальные используют исходники и изолированные тестовые данные.
- Не удаляем пользовательские файлы для тестирования, не меняем базы разрешений macOS и не обходим системные ограничения.
- Предположение по коду, автотест и живая проверка интерфейса — разные виды доказательств. Отмечаем их отдельно.
- Внешние сообщения, публикации и работа с аккаунтами выполняются только в пределах разрешённой пользователем задачи.
- Главный статус продукта — docs/STATUS.md; подробные доказательства — документ приёмки конкретной версии. Нельзя объявлять релиз готовым по одному успешному тесту или сборке.

## Начальный этап

Аудит текущей версии 1.2: пользовательские сценарии, дизайн, согласованность документации и оставшиеся проверки. Создание команды само по себе не запускает очистку, замену установленного приложения или публикацию релиза.

Эти описания ролей сохраняются в репозитории. При новой сессии ведущий разработчик проверяет доступность агентов и при необходимости создаёт их заново; постоянная фоновая работа не предполагается.
