# Оптимизация и сброс контекста — границы операций

## Предлагаемый интерфейс

1. **Оптимизировать для продолжения** — проверенная копия, сводка действующих целей/ограничений/решений/ошибок, ссылки на исходник, последние обмены сообщениями и перенос в новый чат. Оригинал остаётся доступен для поиска. Это уменьшение рабочего контекста, не обещание освобождения места на диске.
2. **Начать с чистого контекста** — сохранить копию и предложить штатное создание новой сессии в агенте. Сводка необязательна. Не переписывать внутреннюю базу или ID сессии стороннего приложения.
3. **Удалить историю** — отдельное явно разрушительное действие; только при поддержанном адаптере удаления и после проверки копии/выбора пользователя. Пока не реализовано.

Сейчас реализованы подготовка отдельного handoff и backup. Автоматическое создание/сброс/удаление чужих чатов ещё не реализованы; интерфейс не должен выдавать их за работающие функции.

## Выводы из прежнего опыта

В найденных локальных отчётах прежняя оптимизация выполнялась из Cursor, но затрагивала CodingAssistant/Codex в Xcode. Для устранения зависаний сохранялась копия, менялась активная сессия, старые потоки архивировались, а UI-история сокращалась до последних сообщений. Это восстановление работоспособности, а не доказанное семантическое сжатие. Повторять манипуляции внутренними plist/ID как универсальную функцию нельзя без адаптера версии, проверки целостности, закрытого владельца и восстановления после сбоя.

## Практики, которые переносим

[Cursor Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery): краткая сводка сохраняет ссылку на полную историю; большие выводы инструментов доступны в файлах и читаются по необходимости. Это снижает риск потери деталей по сравнению с необратимым обрезанием.

Критерии реализации: раздельные действия и метрики (токены рабочего контекста / физическое место), действующие требования отдельно от отменённых, проверяемые ссылки, отдельная копия, возможность восстановления, отсутствие обещания «без потери смысла». Удаление и SQLite VACUUM не являются сжатием смысла. Наличие большого файла БД само по себе не означает, что его можно безопасно удалить.
