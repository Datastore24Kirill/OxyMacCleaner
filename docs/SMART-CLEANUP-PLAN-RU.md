# Интеллектуальный поиск возможностей очистки

Дата: 6 октября 2026. Дополнение к ТЗ OxyMac Cleaner.
Статус на 0.4.7: это дополнение к ТЗ первой версии, а не отдельный проект после него. Уже реализованы снимок и карта диска, карантин, первые правила файлов, сводка Xcode/симуляторов/дубликатов, проверяемая очистка узких проектных кэшей и защищённых worktree. Каталог зависимостей расширен, но остаётся только для просмотра. Не реализованы универсальное определение владельца произвольных данных, семантические пояснения модели и автоматическое удаление.

## Что изучили у конкурентов

Изучена публичная документация, а не внутренние алгоритмы. Ниже — наблюдаемые функции, затем наш собственный проект решения.

| Продукт | Подтверждённый подход | Что используем как ориентир |
|---|---|---|
| [CleanMyMac: Large & Old](https://macpaw.com/support/cleanmymac/knowledgebase/large-and-old) | Группировка крупных файлов по типу, размеру и дате доступа; просмотр и выбор пользователем | Фильтры и объяснимый список кандидатов, без автоматического выбора личных данных |
| [CleanMyMac X: Space Lens](https://macpaw.com/support/cleanmymac-x/knowledgebase/space-lens) | Визуальная карта размеров, переход внутрь папок, отдельный просмотр выбранного | Разделяем изучение диска и подтверждение действий |
| [DaisyDisk: Purgeable space](https://daisydiskapp.com/guide/4/en/PurgeableSpace/) | Отдельно объясняется очищаемое системой место и задержки его пересчёта | Не выдаём системный резерв и логические размеры за немедленно освобождаемые байты |
| [Nektony Disk Space Analyzer](https://nektony.com/help/disk-space-analyzer) | Диаграмма структуры диска и навигация по занимающим место объектам | Визуальная карта плюс доступный текстовый список |

Не копируем фирменную графику, закрытые правила или обещания безопасности. Не делаем вывод «старый = ненужный». Дата изменения в первой реализации не называется датой последнего использования.

## Пользовательский сценарий

После сканирования появляется отдельный раздел «Возможности очистки». На карточке: причина, объём, уверенность, риск, условия выполнения, способ восстановления и действие «Посмотреть». Выбор по умолчанию пустой.

Группы: «Восстановимые данные разработки», «Стоит проверить», «Дубликаты», «Требует закрытия приложения», «Защищено». Большие личные видео и фото относятся к просмотру, не к мусору.

Перед выполнением — единый список конкретных объектов и последствия. Обычные файлы и поддержанные папки идут в карантин. Симуляторы — отдельный сценарий поддерживаемых инструментов. Напоминания о карантине остаются раз в пять дней.

## Алгоритм v1: локальные проверяемые правила

1. **Инвентаризация.** Используем снимок сканирования: пути, размеры, идентификаторы файлов, даты, объём доступных данных и пропуски. У каждого снимка есть время; устаревший снимок не является разрешением на удаление.
2. **Определение владельца.** Приложение, проект, Xcode, runtime, агент, пользовательские медиа. Тип файла внутри пакета не переопределяет владельца.
3. **Запреты до ранжирования.** Исключения и закреплённые объекты; исходники и секреты; работающие базы; активные сборки/симуляторы; изменённые worktree; неизвестный формат; недоступные данные. Неизвестная активность не считается отсутствием активности.
4. **Доказательство кандидата.** Каждое правило возвращает версию правила, идентификаторы объектов, наблюдаемые признаки, причины, способ восстановления и условия. Для дубликатов — проверка содержимого; для архива — приложение/версия/dSYM/правило хранения; для зависимостей — распознанный проект и воспроизводимая установка.
5. **Устранение пересечений.** Если выбран целый каталог, его дочерние файлы не увеличивают сумму повторно. Жёсткие ссылки и APFS shared blocks учитываются отдельно; неизвестную физическую экономию не заменяем логической суммой.
6. **Ранжирование.** Сначала класс риска, затем полнота доказательств, затем ожидаемый эффект и стоимость восстановления. Не используем единственную «магическую оценку», способную поднять опасный объект наверх из-за большого размера. Внутри одного класса сортируем по объёму, при равенстве — по давности изменения.
7. **Предпросмотр.** Показываем логический объём, доступную оценку занятых блоков, размер карантина и неопределённость фактического освобождения. Для N архивов выводим сохраняемые и предложенные экземпляры по каждому приложению.
8. **Повторная проверка перед действием.** Существование, тип, путь/ссылки, идентичность, размер, дата, принадлежность тому, активные процессы, исключения и последняя копия. При изменении данных действие прекращается до нового анализа.
9. **Журнал и восстановление.** План операции фиксируется до переноса. Успех сообщается после проверки целостности. Отказ/прерывание оставляет понятный восстанавливаемый статус. Фактическую экономию измеряем отдельно после окончательного удаления, с оговоркой о сторонних изменениях свободного места.

## Первые правила

| Правило | Минимальное доказательство | Ограничение |
|---|---|---|
| Старые установщики в загрузках | Распознанное расширение, расположение, возраст | Только предложение проверить; файл может быть нужен офлайн |
| Точные дубликаты | Сравнение содержимого, сохраняемая копия | Не объявлять зависимости разных проектов взаимозаменяемыми |
| DerivedData | Распознанная структура Xcode, проект, отсутствие активной сборки | Указать цену повторной сборки |
| Архивы Xcode сверх N | Метаданные приложения и версии, дата, dSYM, закрепления | Не удалять единственные нужные символы; ручной выбор |
| Зависимости и результаты сборки | Проверенный адаптер типа проекта, файлы восстановления | При сомнении — только анализ |
| Неиспользуемые симуляторы | Реальная инвентаризация, связи runtime/device, состояние | Не трогать запущенные; показать потерю тестовых данных |
| Старые worktree | Проверка Git, локальных изменений и использования агентом | Незакоммиченное/непроверенное блокирует рекомендацию |
| Данные агентов | Адаптер конкретной версии, тип данных, отсутствие активной записи | Истории и базы не переписываются; сокращение отдельно от удаления |

«Брошенные данные приложения» не определяются только отсутствием .app в /Applications: приложение может находиться в другом месте или иметь общие данные. Системные snapshots, swap и sleep images не входят в автоматическую очистку.

## Роль локальной модели

Для первого набора правил модель не обязательна. В последующем Ollama может объяснять уже проверенные признаки понятным языком и группировать рекомендации. Модель не определяет произвольные пути удаления, не запускает команды, не отменяет запреты. Имена файлов и тексты историй считаются недоверенными данными. Весь анализ остаётся локальным.

## Этапы и критерии приёмки

1. **Основа:** сохранение снимка, карта диска, фильтры. Снимок переживает перезапуск; частичный обход остаётся частичным; испорченный файл не принимается молча.
2. **Безопасное выполнение:** карантин папок, журнал восстановления и испытания сбоев. До этого правила каталогов работают только в режиме анализа.
3. **Первые рекомендации:** загрузки, точные дубликаты, DerivedData. Каждая рекомендация объяснима и имеет проверенные тестовые примеры и контрпримеры.
4. **Xcode/проекты:** архивы, устройства, зависимости и worktree. Активная работа и несохранённые изменения блокируют очистку.
5. **Агенты:** адаптеры известных форматов; локальные пояснения по желанию. Оригинальная история сохраняется.

Обязательные проверки: пересечение родителя и ребёнка; симлинки и смена файла после анализа; hard links; отсутствие доступа; отключение тома; нехватка места; прерывание переноса; конфликт восстановления; пустой/неполный снимок; отсутствие локальной модели; подмена инструкции в имени файла; отсутствие сетевой отправки содержимого. Все destructive-тесты — на созданных тестовых данных.

Метрики до выпуска: точность распознавания на размеченном наборе, число ложных рекомендаций, полнота запретов, время анализа и пиковая память. Процент «безопасности» без измерений пользователю не показывается.
